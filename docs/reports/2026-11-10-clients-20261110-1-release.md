# Release clients-20261110-1 (2026-11-10)

Windows client 0.1.20.79 with two fixes. Not forced: no `client_update`
field, no minimum version; GUI users update on their own click.

## What ships

| Component | Before | After |
|---|---|---|
| Windows app (setup) | 0.1.20.78 | **0.1.20.79** |

Everything else (headless, macOS, Android, iOS, Linux agent, Ultra runtime
2026.11.1 `94c91be1`) is unchanged. The setup's helper payloads are
byte-identical to 0.1.20.78; only the app assemblies differ, so there is no
attestation rollover.

## Fixes

1. **Sign-out froze the app; killing it kept the session**
   (fix/windows-signout-hang `2f320879`).
   - Sign-out blocked the WPF UI thread on the proxy stop
     (`Task.Run(...).GetAwaiter().GetResult()`) while background cleanup
     marshalled back with a synchronous `Dispatcher.Invoke`. A proxy start,
     forward health check or reconnect could also hold the proxy gates with
     its next step queued to the blocked UI thread.
   - The config was saved only after teardown, so killing the frozen app left
     the agent token in `config.json` and the next launch was signed in.
   - Now: the cleared login is persisted before any teardown; sign-out awaits
     `MainViewModel.SignOutAsync` (20 s proxy-stop budget) instead of blocking;
     an in-flight reconnect is force-cancelled; `InvokeOnUiThread` posts with
     `BeginInvoke`.
2. **Non-ASCII machine name broke every panel call**
   (fix/ascii-safe-device-headers `afdbd5d4`).
   - A Chinese machine name put a non-ASCII value in `X-Device-Name`; .NET
     rejects that at send time ("Request headers must contain only ASCII
     characters"). The client now sends such names as an RFC 2047
     `=?UTF-8?B?...?=` encoded word.
   - Panel half (`ClientOnlineSessionService::decodeHeaderText`) decodes it.
     The release tool does not write PHP; until that file is deployed the
     panel shows the encoded string as the device name (display only).

## Review of the remaining sign-out paths

An audit of every call reachable from sign-out found further gate waits that
could still stall a *blocking* caller (native/normal proxy start, forward
health check, reconnect, MTU apply, native lease refresh). Sign-out no longer
blocks the UI thread on any of them, and the proxy stop is bounded at 20 s.
Not fixed in this release: the update-install path and `OnClosed` still call
the blocking `StopProxyForShutdown` (no UI button binds `DisconnectCommand`;
the dashboard disconnect awaits `StopProxyAsync`);
`WindowsProxyConnectionService` awaits lack `ConfigureAwait(false)`;
`NativeOutboundRelayHost` waits for exit without a timeout.
