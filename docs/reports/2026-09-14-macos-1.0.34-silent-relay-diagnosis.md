## 一句话结论

**升级确实生效了，但升级不可能修好现在这个问题——故障不在客户端。**
1.0.34 内嵌的 Ultra runtime 是全网最新的 `2026.09.13.3.452c8fe8`（哈希已逐字节核对），
09-13 那轮"静默候选隔离"修复已经在里面并正在工作；它把 09-13 的"监听端口反复消失 / 无限重连"
修掉了（`not listening` 告警 493 → 2）。现在剩下的症状是**中继侧收下握手、收下请求、
一个字节都不回**，而同一个二进制、同一台机器、同一时刻另一个 forward 完全正常。

## 3. 为什么可以判定"不在客户端"

1. **握手是成功的，而且是被中继确认过的。**
   `dialStreamWithGreetingUntil`（`tools/ultra-client/main.go:445-483`）在读到中继的
   `05 02 01 00` 或 14 字节 prelude 之前不会返回连接
   （`readStreamAcksUntil`，`main.go:281-336`）。中继若拒鉴权会回 `05 02 01 01`
   → `errStreamAuthenticationRejected`；若直接关连接 → 握手 EOF → 客户端记为
   **setup failed**。日志里 `authentication rejected` / `prelude rejected` /
   `command rejected` **全天真零次**，`tcp candidate failed` 全天只有 3 条。
   → 所有被观察到的 SILENT 流都是**已经建好、中继已经 ACK** 的流。

2. **runtime 里没有任何约 1 秒的定时器能结束一条已建立的 TCP 流。**
   逐条审计 `tools/ultra-client` 非测试代码的全部时间常量：唯一的 1 s 分别属于
   UDP warm 重试（`main.go:1477`）与 UDP-ASSOCIATE 的 socket 读超时
   （`native_socks5.go:759/772`），与 TCP 中继路径无关；最近的一个派生值是
   `5s/4 candidates = 1.25s` 的**拨号**预算（`ha_candidates.go:228-231`），它失败时
   产生的是 setup failed，不是"已建流零下行"。观察到 ~1000 ms 的关闭发生在对端。

3. **同一时刻、同一账号、同一台 Mac 上，另一条 forward 完全正常。**
   两个 runtime 进程是同一个二进制、同一份配置生成器。13:15–13:17 fwd 185 每 20 秒
   稳定完成一次 90 ms 上行 + ~1.1 s 下行 1770 B 的交互，fwd 184 全灭。

4. **老流在跑，新流全死。** 13:15:06 旧 generation `224aab4284` 的长连接一次性收到
   10572 字节下行，而此刻 `9c69a3bce1` 的新流一个字节都收不到。
   这是"中继新建连接能力异常"的典型签名，不是本机断网、不是账号失效。

5. **generation 轮换不可能是原因。** generation / selection_ref / lease ticket
   **从不上线**——`buildHandshakeWithGreeting`（`main.go:158-178`）只把
   lease 的 user/password + 目标地址发给中继，其余字段全是 runtime 本地的日志/健康元数据。
   所以面板换发 ticket（`scripts/panel-patches/01-accept-rotated-lease-ticket.php`）
   只会在**领租约**这一步产生 409，不可能造成"握手成功但零回包"。该 patch 至多是
   抖动的加重项，不是零字节机制。

## 4. 客户端确实还存在一个放大器（这条要修）

runtime 把"中继收下数据不回包"当成**线路**故障来隔离，方向是对的，但爆炸半径失控：

```go
// tools/ultra-client/ha_candidates.go:128-168
window := pathIsolationWindows[index]      // 15s → 45s → 2min
s.isolated[stateKey] = now.Add(window)
if s.allPathsIsolatedLocked(protocol, now) {
    // 只清了 streak，没有清 isolations
    s.pathFailures = map[string]int{}
}
```

- 注释假设"隔离本身至多一个第一档窗口"（15 s）；但 `index` 会随 streak 升到 2，
  即 **已连续失败的路径可以被锁 2 分钟**，而"全部隔离"的重置并不缩短它。
- `ClearPathFailure` 只在**有下行字节**时调用（`ha_tcp.go:87-90`）。全部隔离 → 没有流能建
  → 永远没有成功 → 只能等时钟。**恢复路径是死锁的。**
- 没有任何"提前探测解除隔离"的机制，隔离只按时间过期。

实测吻合：13:15:18 全部隔离 → 13:17:49 最后一条 setup failed = **151 秒整段死掉**，
而中继其实在 1 秒级的抖动里就可能已经恢复。09-13 之前没有这套逻辑时，同样的静默只表现为
"1 秒重连风暴"（`81f66ff9` 的提交说明），用户感知是"一直报错"；现在变成"整条线路确定不可用 2 分钟"，
观感更差。

| 假设 | 结论 | 依据 |

# 附录 A：已实施的修复（隔离放大器）

改动文件：`tools/ultra-client/ha_candidates.go`、`tools/ultra-client/ha_dead_stream_test.go`

## A1. 问题（对应 §4）

`failPathLocked` 在"全部路径都被隔离"时只清空 `pathFailures`（streak），
**没有收敛 `isolated` 里已经升级过的期限**：

- `index := streak - minStrikes` 会升到 2，即 2 分钟档（`ha_candidates.go:149-158`）；
- 清空 isolation 的唯一途径是"有一条流收到下行数据"（`ha_tcp.go:87-90` → `ClearPathFailure`），
  而全部隔离时根本无法建流 —— **恢复路径是死锁的**，只能等时钟。

代码注释声称"isolations 自己会过期（至多第一档窗口）"，但这只对从未升级过的路径成立。
实测：13:15:18 → 13:17:49，**151 秒**完全无候选。

## A2. 修法

新增 `collapseGlobalOutageLocked`，在检测到"该协议下已无可用路径"时：

1. 依旧清空 streak；
2. 把该协议**所有已授权路径**的隔离期限收敛到 `now + pathIsolationWindows[0]`（15 秒）。

同时抽出 `authorizedPathKeysLocked()`，让"全部隔离"判断与收敛共用同一份授权路径集合，
顺带保证收敛只作用于当前 lease 授权的路径。

刻意**不**选择"全部隔离时立即放行"：那会退回 `81f66ff9` 修掉的 1 秒重连风暴。
第一档窗口既保住重试节流，又把黑洞上界从 2 分钟压到 15 秒。

## A3. 验证

| 项 | 结果 |
| --- | --- |
| 新增回归测试 `TestGlobalOutageCollapsesEscalatedWindows` | 通过 |
| 临时把修复改回旧行为后跑同一测试 | **失败**：`first path stays isolated for 2m0s after a global outage; want at most the first window 15s` |
| 恢复修复后再跑 | 通过 |
| `gofmt -l ha_candidates.go ha_dead_stream_test.go` | 无输出（干净） |
| `go vet ./...` | 通过 |
| `go test -count=1 .`（全包） | `ok leikwan.local/ultra-client 156.518s` |

## A4. 发布注意

这是 **runtime** 改动。1.0.34 内嵌的 `2026.09.13.3.452c8fe8` **不含**此修复，
macOS / Windows / Android 都需要重新构建 runtime 并重新发版才能到用户机器上。

## A5. 未做（等确认）

- 半开探测（在窗口到期前放一条探测流）：改动面更大，先不做。
- §6.4 的"把静默拆成两类证据"（中继已 ACK 后零字节 vs 握手都没过）：会影响候选信誉上报，
  需要和面板侧的归因一起改。

# 附录 B：后台 ultra lines「非常少」的成因

> 这句话有两种读法，指向两个不同的界面和两个不同的成因，需要先确认在看哪个界面。
> 下面两条都已核对到具体代码行。

## B1. 组合选择器 / 客户端候选池里很少 → `is_enabled` 派生门禁

- 每次上报库存都会**重新计算** `is_enabled`，判据是源端自报的分类
  （`master/src/Support/UltraInventoryService.php:156`）：
  ```php
  'is_enabled' => $rawAccess === 'native_udp' && $rawNativeState === 'verified' ? 1 : 0,
  ```
- 迁移 `master/migrations/20260831_add_ultra_line_quality_classification.sql:27-30`
  把**所有**不满足 `access_class='native_udp' AND native_udp_state='verified'` 的行
  `is_enabled` 强制置 0。
- 所有"可用于投放"的界面都要求 `is_enabled = 1`：
  `AdminController.php:2707-2710`（组合选择器，否则显示 "No enabled Ultra inventory lines."）、
  `UltraMaterialService.php:55-58`、`ProvisioningService.php:4277-4280`（客户端候选池）。
- 源端对**从未审计过**的线路默认填 `unknown`
  （`source-agent/ultra_source_agent.py:711-716, 395-397`）。

→ 行的确存在、也被统计，但**只要源端没有把它标成 native_udp + verified，它就永远进不了
组合和客户端候选池**。这条同时也解释了 09-13 报告里"30 分钟领 1197 张 lease，只有 5 个不同候选"。

## B2. Lines 列表页看着很少 → 默认 50 行 + 界面没有翻页控件

- `AdminController.php:3136-3138`：`limit = min(200, max(1, input('limit', 50)))`，
  并且**确实**读了 `?page=` 算出 offset，传给 `listLinesForAdmin`（`:3180`、`:3277`）。
- `UltraInventoryService.php:356-414`：默认 `WHERE ul.is_source_present = 1`，
  `LIMIT $limit OFFSET $offset`。
- 但整个 `AdminController.php` **没有任何一处输出 `page=` 链接**（grep 命中 0），
  页面不渲染翻页控件 → 只能靠手改 URL 才能看到第 51 行之后。
- 另外 `is_source_present = 0` 的行默认不显示（`:360-362`）；源端一次"不完整"的库存上报
  会把缺失行全标成 absent（`UltraInventoryService.php:219-224`），列表会突然塌掉，但行还在。

对照：页面顶部 summary 卡片来自**全表**统计（`summaryCounts`，`:525-554`，无过滤无分页），
其中 "Available lines" = `is_source_present = 1` 的行数。
**"卡片数字很大、下面列表很短" → B2；"卡片数字本身就很小" → 查 B1。**

## B3. 自查 SQL

```sql
SELECT COUNT(*) AS rows_total,
       SUM(is_source_present = 1) AS present,
       SUM(is_source_present = 1 AND is_enabled = 1) AS usable,
       SUM(is_source_present = 1 AND is_enabled = 0) AS present_but_disabled
FROM ultra_lines;

SELECT is_source_present, is_enabled, access_class, native_udp_state, COUNT(*) c
FROM ultra_lines GROUP BY 1,2,3,4 ORDER BY c DESC;
```

若 `present_but_disabled` 很大 → B1；若 `present` 远大于 50 → 先看 B2。

## B4. 其它已知上限（可能叠加）

- 单源库存硬上限 256 行：源端截断并置 `complete=false`
  （`source-agent/ultra_source_agent.py:640-643, 930`），面板对 >256 直接 422
  （`UltraInventoryService.php:171-173`）。
- 客户端候选池每条 forward 最多 8 条（`ProvisioningService.php:4298`、
  `LeigodTokenBroker.php:252, 282`），且要求 `ultra_sources.is_active = 1` 与材料未过期。
- `UltraMaterialService::requiredLineIds` 用 `SELECT DISTINCT ul.line_id`
  （`UltraMaterialService.php:49-70`），会把**不同 source 下的同一个 line_id 折叠成一条**。

## B5. 与本次故障的关系

客户端日志侧：2026-09-14 一天里 forward 184 被下发了 **154 + 59 个不同 selection_ref**、
122 个不同 generation；两个 forward 合计在 UDP 探测失败行里出现过 **29 个不同中继 IP**。
注意 `relay_ips_json` 每行最多 8 个 IP，所以 29 个 IP **不等于** 29 条线 —— 这里不能直接当线路数用。

结论：**"客户端实际在用/在试的中继"与"后台可投放的 ultra lines"是两套数**——
前者由面板候选池（≤8/forward）与租约轮换决定，后者由 `is_enabled` 门禁决定。
要判断谁少，先按 B3 跑一次 SQL，并告诉我具体看的是哪个界面（Lines 列表 / 组合选择器 / 其它），
我按那个界面的取数路径继续查。

## E2. 由此确认的第二个独立故障（缺陷 #4）

**一次短暂的租约刷新 409 会把整条 forward 的监听器完全拆掉，而不是降级服务。**
序列是：面板 409 `policy_unavailable` → runtime 取消策略 → 监听停止 → 本地连接被拒
（约 40 秒）→ 客户端探测到 `local port not listening` → 排队 recovery → 恢复。

这和用户生产日志里的序列**是同一个机制**：
12:48:02 `policy_generation_invalid` → 12:48:43 批量 `direction=runtime reason=canceled`
→ 12:48:54 `forward 184: local port 10809 not listening`（见附录 D5 与 §3）。

因此 409 在 8 段静默里只对 1 段有解释力（作为**独立的**故障源），但它自身就是一个用户可见的
中断源，值得单独修：**租约刷新失败时应当保留旧策略继续服务，而不是取消 runtime。**

# 附录 F：缺陷 #3 已确证并修复（headless 停机不回收子进程）

2026-09-14 Mac 100.103.253.21（1.0.34，macOS 26.6.2 arm64）定向复现，原始证据在 `~/diag1/`：

```text
headless pid=30485  pgid=30471
  ultra-client 子进程 ppid=30485, pgid=30471（全部与父同组；spawn 时四条都打了 process_group_create_failed）
    30515 fwd 171 :32502 | 30520 fwd 158 :30522 | 30525 fwd 159 :32469 | 30530 fwd 170 :10001
17:47:17  只向 30485 发 SIGTERM
t+1s      headless 已消失；3 个子进程仍存活
t+20s     "stopping macOS processes for forward" 只出现 1 次（forward 159）
          "stopped macOS processes for forward" 出现 0 次
          30515 / 30520 被 reparent 到 PID 1，**且仍占着 30522 与 32502 在 LISTEN**
```

**根因**：`MacHeadlessSignals.Register` 的 POSIX 注册用了 `_ => Handle("SIGTERM")`，
**丢弃了 `PosixSignalContext`、从未设置 `context.Cancel = true`**。
`PosixSignalRegistration` 的处理器返回后，默认处置（终止进程）照常执行——
所以优雅退出最多只走到第一条 forward 就被打断。
同文件 Windows 分支的 `Console.CancelKeyPress` 一直有 `eventArgs.Cancel = true`，POSIX 分支漏了。

**后果**：客户端停/重启后残留 ultra-client 仍占着监听端口，下次启动撞 `ultra_port_conflict`
（用户生产日志里反复出现的 `local port ... not listening` 与 `process_group_create_failed` 同源）。

**修复**：`LeikwanBridge.Desktop/src/LeikwanBridge.Mac/Services/MacHeadlessHost.cs`，
三条 POSIX 注册统一走 `Graceful(...)`：先置 `context.Cancel = true` 再触发取消，
让 `RunAsync` 里的 `await StopAsync(...)` 真正跑完。已 `dotnet build -r osx-arm64` 通过（0 warning / 0 error）。

这条修复**不在** `2026.09.14.1` 的发布里（那是 runtime 改动）；它要等下一个客户端版本（1.0.36）。

## F1. 缺陷 #4 的状态（未定论）
