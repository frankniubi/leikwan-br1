- **Linux**：agent 读 `desired_ultra_runtime_sha256`（面板按清单算）→ 自更新。发布清单即生效。
- **macOS**：保持 **1.0.31 版本号不变**，只把更新包重打成新 runtime 并改 `bin/ultra-client` pin。
  客户端逻辑是「版本不新但 runtime 漂移」也会更新，所以运行时可以单独换；
  重打用 `scripts/repackage-macos-update.py`（替换 runtime → rcodesign 双签 → 刷新 helper-manifest → 重打包 → 审计

## 事故：面板数据库连接耗尽（05:14Z，已恢复）

- 现象：主站与镜像 `/artifacts/*` 与 `/api/health` 全部 500，错误为
  `migration_failed` at `MigrationRunner.php:115`。
- 真因：**MariaDB `max_connections=151` 被打满**（`Threads_connected=152`）。
  `v3_leikwanhost_c` 一个库占 ~130 条（三个 PHP-FPM 池的 worker 常驻连接），
  加 wiki 24 + buy 17 直达上限；新连接（含引导期 `ensureHistoryTable()`）直接 `1040 Too many connections`，
  于是每个请求都抛 `migration_failed`。**迁移并无积压**（`schema_migrations` 94 条，最新 = 20260914，04:42:30）。
  锁等待为 0，不存在死锁。
- 诱因：本轮发布同时进行了 ~230 MB 上传 + 89 MB APK/13 MB runtime 的并发下载，叠加设备轮询突发。
- 处置：`SET GLOBAL max_connections = 500` → 连接数立刻从 152 回落到 16，主站与镜像恢复 200；
  并持久化到 `/etc/mysql/mariadb.conf.d/99-leikwan-limits.cnf`（`max_connections = 500`，重启后仍生效）。
- 待办：三个 PHP-FPM 池的 `pm.max_children` 之和与 DB 上限应留出余量，建议下一轮复查（本次未改动 FPM 配置）。
