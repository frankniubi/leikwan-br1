## 客户端拿到修复的路径

1. **Linux 主机**：agent 轮询 `desired_ultra_runtime_sha256` / `desired_install_forward_runtime_sha256`，
   发现哈希变化后自更新并重启 forward 服务 → 新的 runtime（带 ceiling 测量与自迁移）+ 新的 overlay MTU 跟随逻辑。
2. **Windows/macOS 桌面端**：`windows_client_app.runtime_sha256` 已指向 `030b4815…`，桌面端 drift 检测后替换
   `bin/ultra-client(.exe)`；TUN MTU 在下次启动/切换时按新 runtime 上报的 ceiling 解析。
3. **Android**：`leikwan-android/app/src/main/assets/runtime/arm64-v8a/ultra-client` 已更新（需随 APK 发布才生效）。

## 未做 / 风险

- macOS 调试器检测只有 DYLD 注入一个弱信号（`P_TRACED` 结构私有，故意不猜）。
- attestation 目前**只报告**：`ULTRA_RUNTIME_FINGERPRINTS` 为空 → 任何会话都是 `unknown`，不改派发、不拒租约。
  要真正拦改包客户端，需要填指纹白名单 + 打开"mismatch 拒发"开关（代码里已留位置，策略待定）。
- 三个限额默认 0（不限）；开之前建议先看 Refusals 页的历史基线。
- `ultra_lease_refusals` 没有清理任务（`master/cli/` 未动），管理页读取 LIMIT 200。
- 桌面端 TUN 不支持在线改 MTU：变更会以 `mtu_update_pending` 暴露，由下一次启动/切换应用；
  在此期间 runtime 会拒发超限数据报（不黑洞），所以旧 MTU 不会造成静默丢包。
