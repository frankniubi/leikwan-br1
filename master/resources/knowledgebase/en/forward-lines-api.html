Who this is for

Use the Forward Lines API when you want your own program or script to manage forwards: creating them in bulk, switching routes on demand, or wiring them into your own system. For everyday changes, the console is all you need.

The API manages the forward itself: which route it uses, which local port it listens on, and where it sends traffic. Nodes, route combinations and tunnel credentials are run by the platform and never appear in the API. The connection itself is still made by the LeiKwan client after it fetches its configuration.

Authentication

Authorization: Bearer <your API token>
  • Only a Bearer token in the request header is accepted. Tokens in the URL are not.
  • Find your API token in the console under Account Security → API token, where you can also reset it. Resetting stops the old token immediately. Treat it like a password and keep it out of your logs.
  • The API token is not the client Agent Token shown on the Clients page. Calling the API with the Agent Token returns 401 user_auth_failed.
  • An invalid token or a disabled account always returns 401 user_auth_failed.

  "transports": ["tcp", "udp", "tcp+udp"],
  "forward_limit": 64,
  "active_forward_count": 2,
  "capabilities": {
    "allow_manage_forwards": true,
    "allow_delete_forwards": true
  },
  "routes": [
    {
      "id": 14,
      "label": "Shanghai–Tokyo",
      "description": "Shanghai → Tokyo",
      "badge": "stable",
      "transports": {
        "tcp":     {"available": true,  "healthy_node_count": 2, "unavailable_reason": null},
        "udp":     {"available": false, "healthy_node_count": 0, "unavailable_reason": "no_healthy_nodes"},

  • routes lists only the routes your plan includes. Use a route's id when you create a forward.
  • forward_limit is how many forwards the service may have active at once; active_forward_count is how many it has now.
  • unavailable_reason is one of route_unavailable, no_healthy_nodes, transport_unavailable or not_configured.

Create a forward

POST /api/v1/user/services/42/forwards
Authorization: Bearer <your API token>
Content-Type: application/json
Idempotency-Key: create-fwd-20261007-01

{
  "route_id": 14,
  "listen_port": null,
  "transport": "tcp",
  "target": {"source": "manual", "host": "203.0.113.10", "port": 443}
}
FieldRequiredMeaning
route_idYesA route ID from step 1
listen_portYesThe local port on the client device, 1–65535, or null to have one assigned
transportYestcp, udp or tcp+udp
targetYesWhere traffic goes; see below (not used for Native Outbound)
native_outboundNoDefaults to false; see Native Outbound

Targets

  • Manual: {"source": "manual", "host": "…", "port": 443}. host is an IPv4 address, IPv6 address or domain name up to 253 characters, without http://, a path or spaces.
  • Another of your services: {"source": "service_ip", "service_id": 43, "port": 8443}. The service must be yours and must have a public IP, and host must be left out. Otherwise fields contains "target.service_id" with not_found, not_allowed (not your service) or no_public_ip (the service has no public IP, such as a Forward Lines service itself).

Some target addresses are refused. Platform nodes connect to your target, so loopback, link-local and cloud metadata addresses are not allowed: 127.0.0.0/8, ::1, 169.254.0.0/16 (including 169.254.169.254), 0.0.0.0 and localhost. These return 422 with "target.host": "reserved_range" in fields. Private ranges such as 10.x, 172.16–31.x and 192.168.x work normally.

curl example

curl -sS -X POST "https://v3.leikwanhost.com/api/v1/user/services/42/forwards" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: create-fwd-20261007-01" \
  -H "Content-Type: application/json" \
  -d '{"route_id":14,"listen_port":null,"transport":"tcp","target":{"source":"manual","host":"203.0.113.10","port":443}}'

A successful create returns 201 with Location and ETag headers and a body of {"ok": true, "forward": {…}}.

Read forwards

GET /api/v1/user/services/42/forwards
GET /api/v1/user/forwards/123

The list contains only active forwards and carries no ETags. Before you update or delete a forward, read it individually to get its ETag. A forward looks like this:

{
  "id": 123,
  "service_id": 42,
  "route": {"id": 14, "label": "Shanghai–Tokyo"},
  "listen_port": 11024,
  "transport": "tcp",
  "native_outbound": false,
  "native_direction": null,
  "target": {"source": "manual", "host": "203.0.113.10", "port": 443, "service_id": null},
  "ingress": {"host": null, "port": null},
  "state": "active",
  "endpoint_count": 1,
  "active_endpoint_count": 1,
  "revision": 3,
  "created_at": "2026-10-07 03:00:00",
  "updated_at": "2026-10-07 03:05:00"
}
  • revision goes up by one on every change; the ETag is "forward-{id}-r{revision}". It may arrive as W/"forward-{id}-r{revision}"; send it back in If-Match exactly as received.
  • ingress is reserved and is always null for now, so don't rely on it. The client fetches its connection details on its own.

Update a forward

PATCH /api/v1/user/forwards/123
Authorization: Bearer <your API token>
Content-Type: application/json
If-Match: "forward-123-r3"

{
  "transport": "tcp+udp",
  "target": {"source": "manual", "host": "backend.example.com", "port": 8443}
}
  • You can change route_id, listen_port, transport and target (in part or in full), and you can turn native_outbound off. Send at least one field.
  • A successful update returns the updated forward and a new ETag.
  • Changing the route, the transport or the target type, or setting listen_port to null, makes the platform re-place the forward. If the route is unavailable you get 409 route_unavailable and the forward stays as it was.
  • To switch between a manual target and a service target, send source together with service_id (or host) in the same request.
  • Every update rebuilds the forward's connections, so don't call it in a tight loop.

Delete a forward

DELETE /api/v1/user/forwards/123
Authorization: Bearer <your API token>
If-Match: "forward-123-r4"
  • A successful delete returns 204 with no body. A stale ETag deletes nothing.
  • Each service keeps up to 512 deleted forwards. Past that, creates fail with 409 forward_storage_quota_exceeded until support clears them, so avoid create-and-delete loops.

Native Outbound

A Native Outbound forward leaves directly from your device instead of going through a platform ingress. Leave target out when you create one:

{"route_id": 14, "listen_port": null, "transport": "tcp+udp", "native_outbound": true}
RequirementError if not met
The route supports Native Outbound and transport is tcp+udp422 native_outbound_requires_ultra_tcp_udp
Your plan includes Native Outbound403 native_outbound_not_allowed
The route has a direction configured422 native_outbound_direction_missing
No other Native Outbound forward on the service uses that direction409 native_direction_conflict

To turn Native Outbound off, send a PATCH with {"native_outbound": false, "target": {"source": "manual", "host": "…", "port": …}}. To turn an existing forward into a Native Outbound forward, create a new one or change it in the console.

Retries and concurrency

  • Reads can be retried freely.
  • If a create times out, retry with the same Idempotency-Key and the same body. You get the original forward back (200) instead of a duplicate.
  • Reusing a key with a different body returns 409 idempotency_conflict. If the original forward was deleted, you get 409 idempotency_resource_inactive.
  • 412 forward_version_conflict on an update or delete means the forward changed. Read it again, check it, then retry with the new ETag.
  • Concurrent creates can never push a service past its forward_limit.

Errors

Every error has this shape:

{
  "ok": false,
  "error": {
    "code": "validation_failed",
    "message": "The forward request is invalid.",
    "fields": {"target.port": "out_of_range"}
  }
}

For validation_failed, fields maps each field to a reason. For unknown_fields, it lists the extra field names, for example ["target.foo"].
