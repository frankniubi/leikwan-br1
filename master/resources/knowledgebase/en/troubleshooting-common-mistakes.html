What you will accomplish

You will start with the symptom you can see, check one boundary at a time, and stop before broad or random changes make the original problem harder to identify.

Before you begin

  • Write down the exact error, time, Client platform, Forward name, and local port.
  • Keep the saved Forward unchanged while you check its current state.
  • Do not include passwords, tokens, generated commands, route keys, private keys, or internal session material in screenshots or support messages.
  • Use the real application protocol for the final test.

The checks move from the Client toward the target. Fix the first failed boundary, retry once, and preserve evidence instead of making random topology changes.

  1. Confirm a recent sync for the expected Client.
  2. Confirm the Forward shows Running.
  3. Check the correct address: use 127.0.0.1 on the same Client device.
  4. For another device, use a reachable Windows or Linux Client-host address. Do not treat Android as a cross-device listener.
  5. Confirm the local port matches the Forward card.
  6. For cross-device use, confirm that only the required port is allowed by the firewall, security group, and NAT as applicable.
  7. Check that the forward and route are healthy in View Diagnostics.
  8. Test the target service from its own host and port.
  9. Retry with the actual application protocol.
  10. If it still fails, collect diagnostics and contact support with the symptom and time.

How to know it worked

The first failing boundary becomes healthy and the real application request succeeds. A recent sync proves configuration delivery, Running proves a local process state, and a successful target response proves the complete request path.

If it did not work

Stop before reinstalling everything, opening broad port ranges, or making random topology changes. Preserve the error and diagnostics. Contact support with the Forward name, Client platform, test time, address type, local port, and sanitized results. Never send secrets.
